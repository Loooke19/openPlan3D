# 医院 2D／3D 导览：项目概览与 PDF 导入技术计划

更新：2026-09-09。用途：交给后续开发者或大模型快速了解项目、按阶段接手。

**状态说明：本文是现状交接与实施计划，不代表下面提出的上传器、编辑器、API 或新依赖已经实现。此次仅编写文档。**

## 1. 两分钟了解项目

用户希望上传一份医院静态布局 PDF，得到可选起终点的电子地图，并切换到三维、模拟真人沿走廊行走。文字使用 SC 简体中文字体，画风不照搬原 PDF；原图图例不进入地图主体。

目前已经做出**岐阜大学医院一楼的专用解析结果和可运行导览 Demo**。已有 2D、3D、导航、材质、贴墙门牌和行走播放控制。缺少的是把任意新文件变成这种数据的通用制作入口。

当前数据快照：64 个地点、52 个房间/柜台/障碍等几何对象、22 个演示门位、710 个图节点、1156 条边。52 个对象不等于 52 个真实科室。

与用户最初参考的 GitHub 项目关系：它是思路参考，不应把本项目当成 Flutter 工程。当前实际前端是浏览器 JavaScript + Three.js，没有 Flutter 运行链路。

**下一阶段目标：单层 PDF → 可编辑草稿 → 人工校正 → 导航图 → 复用当前 2D／3D。不是任何图纸一次上传就准确识别的全自动产品。**

## 2. 已实现与未实现

### 已实现

- 针对当前 PDF 的文字、矢量几何提取及人工/模型审核过的地点标注。
- 原生 SVG 2D 地图，以及共享同一几何数据的 Three.js 三维模型。
- 地点搜索、设施分类、起终点选择、交换方向、Dijkstra 寻路、路线前进箭头。
- 临时关闭通道并重新寻路、两点比例标定、JSON 导入与导出。
- 第一人称沿路线模拟行走；暂停/继续/结束；0.5×～3× 速度；进度条跳转。
- 浅色哑光程序化墙地材质、浅绿墙裙、踢脚线、地砖缝与柔和阴影。
- 贴墙门牌和左右/前方参考提示。当前规则为每个可放置门牌的房间最多两块，路线经过附近房间时优先把一块移到路线侧墙面；未知名称标为未命名房间加 ID。
- 本地 Three.js、Ambient CSS、Noto Sans SC 字体，不依赖页面运行时的模型 API。

### 未实现或不可声称已完成

- 网页上传 PDF、选页裁剪、通用自动识别与完整人工地图编辑器。
- 任意扫描图 OCR 流水线、通用颜色/符号理解。
- 完整项目保存恢复：当前 localStorage 主要保存通道关闭与标定，不是整个导入文件和编辑工程。
- 室内实时定位、跨楼层路线、自由位置 NavMesh 导航、BIM、真实门位及无障碍通行认证。
- 真实人体半径、真实尺寸、医院现场通行状况的测绘验证。

## 3. 当前真实技术栈

| 层级 | 当前技术 | 说明 |
| --- | --- | --- |
| 网页 | HTML、原生 CSS、JavaScript ES Modules | 没有 React 构建应用；用户允许后续引入 React |
| UI 样式 | 本地 @ambientcss/css 3.0.1 | 使用 CSS 包，不是 React 组件包 |
| 2D | SVG | 多边形、文字、图标、路线、点击交互 |
| 3D | 本地 Three.js、OrbitControls | 墙体实例化、标准材质着色器扩展、透视/正交相机 |
| 字体 | 本地 Noto Sans SC 可变字体子集 | 新增中文文案后需检查字形覆盖 |
| 寻路 | 自有 JavaScript Dijkstra；Python 侧图构建/校验 | 图沿可走区域，不让曲线平滑穿墙 |
| PDF 构建 | Python 3.10+、pdfplumber、NumPy、Pillow | 当前专用 profile 和语义 annotations 驱动 |
| 数据 | JSON；配套 TypeScript 类型声明 | 类型声明不等于整个项目已经 TypeScript 化 |
| 持久化 | 文件 + 浏览器 localStorage | 仅有部分设置恢复，不是数据库或完整工程保存 |
| 预览服务 | Python http.server | 只用于本地静态预览，没有上传业务 API |
| 测试 | Python unittest、Node 内置测试 | 最近前端运行 15 项通过；已有 Python 9 项历史通过记录 |

`requirements.txt` 当前约束为 NumPy >=1.24,<3、Pillow >=10,<13、pdfplumber >=0.11,<0.12。字体子集脚本另外依赖 fontTools 和 WOFF2 支持；不要认为装完 requirements 就包含字体制作依赖。

## 5. 不能破坏的坐标和语义约定

1. `schemaVersion` 当前为 `1.0.0`。扩展需考虑兼容，不要直接要求旧查看器读取完全不同格式。
2. 几何坐标按**原始完整 PDF 页面**归一化至 0～1，原点左上，包含原页图例区域；裁剪只影响显示/处理范围。
3. 当前 PDF 为 800×1210。`viewer.js` 仍存在 800、1210 和固定初始视窗等专用值；通用导入前必须参数化。三维已经读取 `source.pdfSize`，不能因此推断整个项目都已适配任意页尺寸。
4. 房间文字位置、房间多边形、走廊到达点、门洞位置是不同数据。不要用房间中心直接作为走路终点。
5. `position` 用于 POI 导航锚点，`labelPosition` 用于标签；门另有 `position` 和 `corridorAnchor`。
6. `opensRoomInterior: false`：演示门位不意味着房间内部开放通行。
7. `lengthMapUnits` 不是米；`calibration: null` 时不得报告真实步行距离、时间或无障碍宽度。
8. `confidence` 当前主要表达名称/符号识别把握，不代表真实门位精度。
9. 孤立区域可以确实不连通，不应为“全可达”硬造走廊或穿墙连线。
10. 新上传文件不能覆盖当前示例及审核数据。源码中的置信度、可空字段和运行时校验还需在通用化阶段对齐。

## 6. 下一阶段建议技术栈（尚未接入）

以下是为本项目给出的工程建议，不是必须同时安装的依赖清单；选型时固定兼容版本，不盲目升级已有 Three.js。

| 职责 | 建议方案 | 理由与边界 |
| --- | --- | --- |
| PDF 页预览 | PDF.js | 浏览器解析/渲染 PDF；不是房间识别模型。[官方文档](https://mozilla.github.io/pdf.js/) |
| 上传与制作 API | FastAPI + Python 类型化请求模型 | 与现有 Python 构建流程衔接；API 层与图处理逻辑分开。[官方文档](https://fastapi.tiangolo.com/) |
| 原生 PDF 内容 | 继续 pdfplumber | 优先复用当前提取路径，先判断是否有可用文字与矢量 |
| 栅格处理 | 先 NumPy + Pillow | 现有掩膜处理基础；更复杂轮廓算法再单独评估依赖 |
| 多边形校验/运算 | 按需引入 Shapely | 几何相交、有效性等检查；无法自动理解哪块是科室。[官方文档](https://shapely.readthedocs.io/en/stable/) |
| 扫描件文字识别 | 后续用 Tesseract 做本地 OCR 基线测试 | 需合适语言数据和真实图纸评估；OCR 给出文字，不提供房间拓扑。[官方文档](https://tesseract-ocr.github.io/tessdoc/) |
| 编辑交互 | 第一版沿用 SVG + 原生 JS | 当前几十个房间规模下先复用，不为增加编辑器立即重写查看器 |
| 更复杂编辑状态 | 可选 React + TypeScript | 用户允许，但并非前置条件；采用时让 UI 层调用原有几何/渲染模块 |
| 工程保存 | 本地文件目录 + SQLite 元数据 | 单机 Demo 的建议，保存原文件、草稿、修订和产物；不是当前已有能力 |
| 寻路/三维 | 复用现有 Dijkstra 与 Three.js | 第一版不必换 NavMesh，也不需接商业室内地图 SDK |

最小增量建议：**PDF.js + FastAPI + 现有 Python/SVG/Three.js**。Shapely 按几何需求引入；OCR 放扫描件阶段。第一版先不引入分布式任务队列、云存储、多租户、实时定位和跨楼层模型。

## 7. 六阶段实施与验收

### 阶段 1：统一数据格式和通用坐标

**工作：**以现有 MapDocument 为兼容输出，另设计制作草稿。草稿记录原文件哈希、页号、原页尺寸、裁剪框、旋转及像素到原页的变换、识别来源、人工修订和待确认项。统一前后端校验，清除预览器固定尺寸假设。

**技术：**JSON、现有 TypeScript 类型、Python 校验模型；先编写数据契约再开发 UI。

**交付：**草稿接口、兼容转换函数、坐标转换函数与样例，不改坏当前 Gifu 地图。

**验收：**至少两种不同尺寸/旋转情况的测试页面，裁剪前后坐标往返一致；旧地图仍能渲染、寻路。

### 阶段 2：上传、选页和裁剪

**工作：**PDF 上传、页缩略图、页面选择、地图范围框选、图例排除；保留完整源文件和裁剪参数，允许重新调整。

**技术：**PDF.js 前端页渲染；FastAPI 文件上传；本地独立工程目录。

**交付：**可保存、恢复的源文件工程。只裁显示范围，不偷换归一化坐标基准。

**验收：**多页文件能选择正确楼层；刷新恢复选页裁剪；无效文件、加密/无法读取文件、超限文件有明确提示。

### 阶段 3：自动生成可编辑草稿

**工作：**先检测 PDF 类型。可用原生文字/矢量优先直接提取；扫描件另走栅格与 OCR。生成房间候选、走廊候选、地点文字及可能关联。白色走廊规则是当前样图假设，不是所有 PDF 的普遍规则。

**技术：**pdfplumber、NumPy、Pillow；按需 Shapely；OCR 分支后加。

**交付：**每个候选附来源坐标、识别方式和待确认原因。不同任务的置信度分开：文字、几何、门位，不混用一个数字。

**验收：**在当前样图和至少一张同类新图上可生成可编辑草稿；图例/文字白色内孔不会轻易成为走廊；错误可被定位而不是静默发布。

### 阶段 4：人工校正编辑器

**工作：**编辑名称、选择/绘制/调整房间多边形、涂改可走区域、拖动/添加门位、指定房间与 POI 关联、撤销/重做、叠加原图核对。

**技术：**SVG 多边形编辑 + Canvas 掩膜涂改；独立编辑状态与操作记录。不要同时让多边形和掩膜互相覆盖而没有优先级规则。

**交付：**编辑草稿可独立保存；人工确认的数据不被重新识别静默覆盖。

**验收：**故意加入错名、断走廊、错误门位，用户都能修复；重开工程保持修改；改几何后旧导航图标记为失效，必须重新构建。

### 阶段 5：生成并校验导航图

**工作：**校正几何生成可走掩膜/安全区域，构建中心线图，门位关联走廊到达点，计算路线；报告断路、无效多边形、孤立 POI、穿墙边和未确认入口。

**技术：**抽出当前 Python 构建逻辑；必要的几何校验；已有 Dijkstra。CPU 密集工作放独立执行过程，不阻塞 API 请求处理。

**交付：**可重复构建的 map.json、验证报告与输入修订号。

**验收：**路线边均落在允许区域、不切障碍拐角；封路后能绕行或明确不可达；不通过增加无依据连线掩盖错误。

### 阶段 6：预览、发布快照和工程保存

**工作：**把通过校验的草稿转换为现有查看器格式；2D／3D、贴墙门牌、路线箭头和行走控制直接复用。保存完整源文件、草稿和生成版本，区分草稿与可查看快照。

**技术：**现有 SVG/Three.js；工程文件 + 元数据存储；版本关联和加载适配层。

**交付：**上传→校正→生成→导览→重开工程全链路。

**验收：**刷新/重启恢复工程；改名同步到列表、2D 和 3D 门牌；改门位后重建路线；失败构建不破坏上个有效快照；另一份 PDF 不覆盖当前示例。

## 8. 建议的模块和 API 边界

以下目录、状态与接口均为**设计提案，当前不存在**：

```text
制作前端：选页/裁剪/编辑/待确认清单
    ↓
API 层：文件校验、项目修订、任务状态
    ↓
处理层：extract → draft → validate → build
    ↓
版本化 MapDocument 快照 → 现有导览查看器
```

- `POST /api/projects`：上传文件，返回工程 ID 和页信息。
- `PUT /api/projects/{id}/draft`：保存带 revision 的选页、裁剪与编辑草稿，拒绝过期修订覆盖。
- `POST /api/projects/{id}/extract`：生成候选草稿，返回任务 ID。
- `POST /api/projects/{id}/build`：按指定草稿修订构建导航快照，返回任务 ID。
- `GET /api/jobs/{id}`：查询阶段、进度、错误和生成版本。
- `GET /api/projects/{id}`：恢复工程元数据和当前修订。
- `GET /api/projects/{id}/maps/{version}`：获取某个已生成快照。

处理状态建议：uploaded → extracting → needs-review → building → ready；失败是独立状态，保留原因和可恢复的输入。无需第一版就做 WebSocket，轮询足够。

安全底线：限制文件大小、页数、渲染像素和处理时间；文件名/ID 不得成为任意磁盘路径；PDF 解析在受限工作进程中执行。即使是本地 Demo，也不执行 PDF 附带内容。没有额外授权时，不把上传文件发送给云模型或第三方 OCR。

## 9. 大模型如何参与，以及怎样节省额度

**确定性程序负责：**提取、坐标转换、几何运算、寻路、渲染、保存。不要让模型生成上千条路线节点替代算法。

**较轻量编码模型负责：**在接口固定后实现上传页、表单、裁剪控件、编辑交互、保存加载和测试。

**强模型按需负责：**阶段 1 的契约/架构审查、复杂图纸语义分析、难解释的连通性问题、最终风险审查。没有必要持续调用强模型处理每一页。

**视觉模型可选：**只看有歧义的局部区域，给候选名称/关联，结果需经过几何校验或人工确认。原图没画出的门，任何模型都不能凭空恢复成真实测量结果。

节省上下文的方法：

1. 先读本文和自己阶段对应文件，不重读整个历史对话。
2. 只做一个阶段，输出接口、修改清单、验收结果和下一步。
3. 以文件哈希和页参数缓存提取结果；不反复 OCR 同一页。
4. 对问题区域截图，不把整份 PDF 每轮提交模型。
5. 维护简短交接状态，保留失败样例，让后续模型按测试复现。

## 10. 当前项目怎么启动和测试

以下命令在项目根目录运行，测试记录仅说明历史结果，不替代每次改动后的回归：

```sh
# 静态预览；如果端口已占用且是现有预览，不要重复启动。
python3 -m http.server 8765 --bind 127.0.0.1

# Python 依赖建议安装到项目虚拟环境。
python3 -m pip install -r requirements.txt
python3 -m unittest discover -s tests -v

# 前端数学/结构测试，README 建议 Node.js 22+。
node tests/test_preview.mjs
```

预览地址：http://127.0.0.1:8765/preview/ 。

**重建会写入产物，接手时不要直接覆盖当前 data/。**先使用独立输出目录，例如：

```sh
python3 scripts/build_map.py --output /tmp/gifu-rebuild-review
```

上述示例使用默认 Gifu 源文件/profile/annotations，仅用于校验当前流水线，不是通用 PDF 导入命令。不要忽略源 PDF 哈希校验，也不要拿旧对象索引套新图。选择一个未使用的输出目录再执行。
