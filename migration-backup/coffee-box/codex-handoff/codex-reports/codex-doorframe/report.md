**结论：问题主要在模型生成阶段引入，输入数据和前端生成规则两者都有责任。最核心的缺陷是：把每条墙记录当成独立实体，只在门的宿主墙上开洞，却没有统一处理重叠墙、相邻墙、接缝和踢脚线。前端还存在独立的门框横梁定位错误，即使输入完全干净也会生成共面。后续修复消除了一部分表现，但没有建立统一的墙体与门洞几何规范。**

建议校准的一处底层规则是：**每个物理墙体区域只生成一次，每个物理门洞只定义一次；所有相交构件共同服从这个门洞的空间约束。** 这比继续调整门框厚度、颜色或深度偏移更接近根治。

证据范围需要说明：当前样例对应 **P1 的 1F、2F、3F**，不是三栋楼。以下能证明共同机制，并提出适用于三栋楼的规则；不能宣称另外两栋已经验证通过。全程只读，未改代码。

**2. 前端生成规则会保留这些冲突，也会独立制造新冲突**

**宿主墙局部切口，没有楼层范围的实体约束。**  
[ThreeViewer.svelte 的 `buildWalls`](/workspace/kit-wt/src/lib/components/viewer3d/ThreeViewer.svelte:3040) 按 `wallId` 筛选门窗，再调用 [buildWallSegments](/workspace/kit-wt/src/lib/utils/wallProfiles.ts:22)。该函数正确地计算了**单堵墙内部**洞口的并集，但不知道另外一堵墙也占据这个空间。`git show HEAD` 确认：向其他墙传播切口是当前未提交修改才增加的。

所以，这里的问题不是某一次矩形切口算错，而是**局部开洞建立在“墙实体互不重复、洞口只涉及一堵墙”的假设上；实际输入不满足这个假设。**

**横梁定位本身错误，干净输入也会失败。**  
HEAD 中门框横梁调用的底部是 `doorHeight`、高度是 `jamb`。普通门高 `210 cm`、框条厚 `3 cm` 时，横梁占据 **210～213 cm**，位于洞顶上方的墙体内；横梁底面与墙洞顶面都在 `y=210`。

[addOpeningFrame](/workspace/kit-wt/src/lib/components/viewer3d/ThreeViewer.svelte:2862) 只按整堵墙的轮廓裁剪，不会把门框限制在门洞内。我用“一堵直墙、一扇门”的干净输入在内存中复现旧规则，得到 **4 对 `wall×frame` 共面三角形**。这证明前端也有独立根因。共面三角形发生深度竞争时，可以显示为浅色三角块；画面看起来斜，不代表模型一定存在真正的斜面。

**踢脚线使用另一套切口规则。**  
[踢脚线生成](/workspace/kit-wt/src/lib/components/viewer3d/ThreeViewer.svelte:3079) 的厚度是 `t+2`，旧代码却仍只按宿主墙门记录的原始区间留空。它既没有共享裁剪后的最终门洞，也没有统一处理其他墙上的洞口；端面还可能与墙洞侧面共面。问题包括宽度增加，也包括切口和端面归属不一致。

**修复增加的接缝圆柱会制造真正的斜面。**  
[addWallJointCaps](/workspace/kit-wt/src/lib/utils/wallJoints.ts:5) 使用 16 段圆柱补墙角，半径来自 [groupWallJointNodes](/workspace/kit-wt/src/lib/utils/doorWallFit.ts:157) 的“最大墙厚一半再加 0.5 cm”。旧版本不考虑门洞。这与上一轮日志直接对应：1F 的 4 个非轴向三角形全部标为 `offAxis:joint`，位于 `door-12/wall-23` 附近。见 [扫描日志](/workspace/kit-trial/door-fix-floor-0.log)。

**另外两点不能误判：**

- 三层输入的墙高全部为 `280 cm`，没有曲墙、没有两端高度差。我也核对了 `createSlopedBoxGeometry` 的三角形绕序与法线，平墙、斜顶墙的样本都一致。因此，这批问题没有证据指向“斜墙函数把所有门洞法线算反”。
- P1 三层的 `windows` 都是空数组。1F 残余 `frame×frame` 对应的是附近门框；`door-37` 与垂直方向的 `door-43` 有构件相交的条件。**不能将这里解释成窗框与门框重叠。**

**4. 最可能的共同根因，以及一处规则校准**

最可能的共同根因是：**逻辑墙记录、补画边界和物理墙实体没有区分；洞口又依附于某个记录，而不是一个统一的空间对象。**

建议在“项目输入 → 生成 Mesh”之间设一个统一的几何规范化阶段，确立以下同一套约束：

- 共线重叠墙归并为物理实体，保留原墙 ID 的映射，并重新投影门窗位置。
- 每个洞口统一定义位置、方向、范围、高度和净通行空间；所有相交墙体、接缝、踢脚线、饰面都受它约束。
- 门框从同一个洞口派生，横梁放入洞口；相交构件共同求解边界，不重复输出内部面和共面。
- 厚度使用统一的有效值。当前渲染隐式取 `max(thickness,15)`，应在规范化阶段明确处理，否则数据拓扑基于薄墙，而渲染实体已经变宽。
- 将亚厘米墙条归入统一的端点吸附容差，并保留可追溯的处理结果。

**这需要校准生成规则，单独调整一个厚度或偏移数值无法覆盖所有类型。** 统一阶段对每栋楼、每层、每个洞口执行相同约束，因此具备一次覆盖共同问题的机制；另外两栋仍必须用完整数据验收。曲墙和合法非正交建筑也应保留其设计形状，不能靠全局强制正交解决。

**5. 验收必须为 0 的指标，以及目前扫描的缺口**

对最终参与渲染的静态几何，以下错误必须为 **0**：

| 指标 | 验收含义 |
|---|---|
| `offAxis`、`offAxisArea` | 矩形门洞内没有非设计的斜面。 |
| `coplanar` | 可见表面没有重复覆盖，包括墙、门框、接缝、踢脚线之间。 |
| `inwardReveal` | 没有违背洞口侧面朝向约束的墙面；此字段不等于已证明顶点法线反了。 |
| 净通行空间被静态实体占据 | 没有其他墙、补面、踢脚线或饰面挡住合法通道。 |
| 重复物理墙体、重复洞口构件 | 不重复生成实体与门框。 |
| 非法微小墙条、退化面 | 没有容差范围内的残条或零面积几何。 |
| 门窗引用与洞口尺寸错误 | 没有失效宿主引用、错误投影或无意缩窄。 |

**目前 `openingAudit` 全 0 仍不足以验收。** [扫描代码](/workspace/kit-wt/src/lib/components/viewer3d/nav/openingAudit.ts:58) 用三角形重心是否在门洞盒内决定是否检查。我做了反例：一堵长 `1000 cm`、完全挡住门洞的实墙，扫描结果仍全部为 0，因为三角形重心落在盒外。

验收前应改为三角形与门洞体积的实际相交检查，并增加净通行空间占用检查；最终扫描还必须包含静态饰面，不能永久跳过 `navKit/navDressing`。同时锁定应存在的洞口、位置和净宽，防止通过删门、删墙让指标归零。**63／41／69 只是当前去重规则下的数量，不能未经核实就作为物理门洞真值。**
